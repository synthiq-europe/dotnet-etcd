# DN-002: Base client design

This document describes the rationale leading to
[lADR-002](../decision-record/002.md).

## Context

The base client lives between the .NET application and an etcd node, possibly
(likely) part of a multinode cluster.

## Design

The context immediately creates two surfaces to define and refine: the client
API, and the transport to the etcd node.

### Client backend

Let's start with the client backend. At the moment of writing, etcd supports two
transport protocols:

- gRPC
- gRPC-Gateway

Most users will likely communicate with their cluster over gRPC, or have the
capability to adjust their infrastructure such that they will be able to.
Implementing two transports would require an abstraction that allows for
shifting between the two protocols, in order not to burden the library
consumer.

This could work using a transport registry, which would likely be familiar to
the consumer, as this pattern is implemented in libraries such as SignalR.
